# gptr-java

[中文](README.md) | **English**

A **deep research service for long-horizon research tasks** (Java 21): a recursive research graph
(LangGraph4j) running on a Postgres task substrate (atomic dequeue + leases + budgets), with a web
dashboard and an auditable evaluator.

> **What one task looks like**: input "how do open-source deep research projects differ in citation
> trustworthiness?", and you get a sectioned report — each section ends with `[n]` citations, the
> source list at the end is generated by code, and every citation points back to the scraped text.
> The dashboard shows each layer of queries and the fetch/verification state of every piece of
> evidence, live.

**Relationship to [gpt-researcher](https://github.com/assafelovic/gpt-researcher)**: the research
pipeline is a Java **rewrite** (not a wrapper); the `crawler/` subdirectory is **extracted** and
reused from that project (Apache-2.0, carrying its own `LICENSE` / `NOTICE`). Per-dimension
differences are in
[Relationship and Differences](#relationship-and-differences-vs-gpt-researcher); literature
borrowings and deliberate deviations are in
[Sources, Borrowings, and Deviations](#sources-borrowings-and-deviations).

**Stack**: Java 21 · Spring Boot 3.5 · LangGraph4j · Postgres · Flyway · MinIO · Resilience4j ·
vanilla-JS dashboard

## Features

**Research**

- **Multi-round recursion, not one-shot Q&A**: clarify the question, then search layer by layer;
  at each layer boundary the engine writes down "what is covered, what is missing", and the next
  layer's queries are generated from that plan.
- **Outline first, then section by section**: each section gathers its own evidence and is written
  on its own, with the already-written sections injected so it does not repeat them.
- **Auditable evidence bank**: every claim carries a verbatim quote and a source URL, persisted as
  JSON — reviewable line by line afterwards.

**Trustworthiness**

- **Only real sources can be cited**: the model may cite only URLs that were both retrieved and
  extracted; out-of-set citations are caught by verification. (In one same-question comparison this
  measured citation consistency 1.00 and contradictory claims 0; sample size and limits are in
  [Same-question comparison](#relationship-and-differences-vs-gpt-researcher).)
- **References are generated by code**: in-text citations are numbered `[n]`, and the source list
  at the end is built programmatically rather than arranged by the model.
- **The judge is calibrated before it is trusted**: the evaluator injects known-answer sentences to
  test the judge first, and only then relies on its scores.

**Engineering**

- **Task substrate**: Postgres queue (atomic dequeue) + lease renewal guard + a three-part budget
  (steps / wall-clock / cost) + graceful retry.
- **Single-page dashboard** (`/dashboard/`): task timeline, cost stats, report reader (rendered /
  raw views), evidence-bank browser, config panel, fork-as-blueprint.
- **Crawl health**: the collected → picked → returned → valid funnel, silent drops, the share of
  citations pointing at pages that were never fetched, plus failure samples.
- **Tests and gate**: engine 248 unit tests · crawler 98 unit tests
  (`python -m unittest discover -s tests`) · benchmark 45 · integration 14 classes / 22 cases;
  a 13-criterion readability gate runs automatically with `mvn test`.
- **No front-end framework or build step**: report rendering uses the vendored `marked` +
  `DOMPurify` shipped in this repository (see [NOTICE](NOTICE)).

## Quick Start

Requirements: JDK 21, Maven 3.9+, Docker (with Compose). Commands are run from the repository root.

```bash
# 1) Multi-module project: install the modules into the local repository first
#    (once is enough; repeat after changing engine/integration/common)
mvn -q clean install -DskipTests

# 2) Infrastructure: Postgres + MinIO + crawler (searxng is an optional retrieval source, see below)
docker compose up -d --build postgres minio crawler
docker compose ps                     # wait until postgres is healthy

# 3) Start the services (two terminals; the default model is mock, so no key is needed)
mvn -pl gptr-worker spring-boot:run   # terminal 1: worker
mvn -pl gptr-api    spring-boot:run   # terminal 2: API + dashboard -> http://localhost:8080/dashboard/

# 4) Submit a task (or just use the page; <id> is the id field in the response body)
curl -X POST http://localhost:8080/api/v1/tasks -H "Content-Type: application/json" \
  -d '{"query":"your research question","config":"{\"mode\":\"deep_research\",\"breadth\":3,\"depth\":2}"}'

# 5) Read the result
curl http://localhost:8080/api/v1/tasks/<id>          # status / cost / errorCode
curl http://localhost:8080/api/v1/tasks/<id>/events   # node activity (ACTIVITY.label = node name)
curl http://localhost:8080/api/v1/tasks/<id>/report   # report body (Markdown)
```

**Three notes** (easy to get stuck without them):

- **The default model is mock**: the report it produces is fabricated and only proves the pipeline
  runs end to end. For a real model, add `--gptr.clients.llm-provider=openai` to the worker and
  supply a key for an OpenAI-compatible endpoint (DeepSeek / OpenAI / Qwen / GLM / local Ollama).
- **You need at least one retrieval source.** If the task does not set `retriever`, the default
  fallback chain runs (in-repo crawler first, then Java-native DuckDuckGo), and DuckDuckGo returns
  nothing in most networks — which shows up as "all sub-queries failed". Two ways out:
  - **Zero cost**: run your own SearXNG — `cp searxng/settings.yml.example searxng/settings.yml`,
    then `docker compose up -d searxng`, and set `"retriever":"searx"` in the task;
  - **With a Bocha key**: put `BOCHA_API_KEY` in `.env` (template: `.env.example`) and set
    `"retriever":"bocha"`.
  (A bare `docker compose up -d --build` also starts searxng, which needs the config file above —
  that is why the commands above name the three base services explicitly.)
- **MinIO console**: http://localhost:9001 (`gptr` / `gptr12345`, local-development defaults only).

Build details, integration tests and troubleshooting: [BUILD.md](BUILD.md).

## Sources, Borrowings, and Deviations

This project read and adjudicated **7 papers** (2025–2026) on deep research. The table below records
the **actual outcome** of each borrowing, marked *implemented*, *consulted*, *deliberately
deviated*, or *rejected* (full titles and links are in
[License and Acknowledgements](#license-and-acknowledgements)):

| Mechanism | Paper | Outcome |
|---|---|---|
| Three-state verdict (Supported / Contradictory / Inconclusive) + counter-evidence criterion | [DeepFact](https://doi.org/10.18653/v1/2026.acl-long.1586) | ✅ Implemented: every evidence sentence reports a three-state verdict plus a verdict allow-list |
| micro-gold judge self-calibration (inject known-answer sentences to test the judge before trusting it) | DeepFact | ✅ Implemented: 30 machine-anchored probes (1:4 adversarial injection) |
| KAE-lite citation coverage (KSR / KCR / KOR + a fourth `abstain` state) | [DeepResearch Arena](https://doi.org/10.1609/aaai.v40i39.40620) | ✅ Implemented: starts from the citations and checks whether the report fully states each key fact |
| "Forbidden sources" per item + leakage-rate reporting (URL blocking at the tool layer) | [DeepResearch Bench II](https://doi.org/10.48550/arXiv.2601.08536) | ✅ Implemented: `blockedUrls` + filtering at the retrieval-result layer (more thorough than the paper, which recommends it but does not ship it) |
| Atomic, content-bearing rubric writing + a self-evaluation gate | DeepResearch Bench II | Consulted (used in the item-bank ingestion flow) |
| Evidence item structure (`insight` separated from `quote`) | [WebWeaver](https://doi.org/10.48550/arXiv.2509.13312) | ✅ Implemented, plus canonical normalization and authorized-set validation |
| Section-wise writing + per-section citation gate | WebWeaver + [FS-Researcher](https://doi.org/10.18653/v1/2026.acl-long.288) | ✅ Implemented. ⚠️ The two papers **disagree**: WebWeaver warns that section-wise writing causes content and style incoherence and argues for inter-section narrative flow; FS-Researcher's ablation finds section-wise strictly better. This project first adopted only the "context isolation" half, then later restored global coherence via already-written-section injection (repetition went down, consistent across two runs) |
| Inter-layer plan reflection / central research state | [Reflect-Evolve](https://doi.org/10.48550/arXiv.2601.20843) | ✅ Implemented: a node that writes "covered vs. gaps" at each layer boundary, read by the next round's query generation |
| Explicit plan + revision allowed | [DeepPlanner](https://doi.org/10.18653/v1/2026.findings-acl.370) | Philosophy adopted (research plan as managed state; its RL training pipeline is not) |
| Distillation / sentence dehydration | WebWeaver | ⚠️ **Deliberately deviated**: the paper uses an LLM to generate a query-relevant summary (lossy, and with no fidelity audit); this project instead does "delete only, never rewrite + a programmatic fidelity pre-check" — because the value of a `quote` is precisely that it is verbatim |
| Write-then-prune | WebWeaver | ❌ **Rejected**: this project does not accumulate evidence (each section takes what it needs), so there is nothing to prune |
| Source-quality gate (curate) | [gpt-researcher](https://github.com/assafelovic/gpt-researcher) `SourceCurator` | ⚠️ When porting we added a prompt input budget the original never had. Measured: once candidates grow, that budget silently drops already-scraped page content (usable content blocks fell from 62 to 34) ⇒ reverted to default-off |

## Relationship and Differences vs. gpt-researcher

`crawler/` is **extracted** (not rewritten); the research pipeline is **rewritten**. What follows are
verifiable structural differences, not adjectives:

| Dimension | gpt-researcher | This project |
|---|---|---|
| Runtime | Python + asyncio, single process | Java 21 + Spring Boot; three processes: api / worker / crawler |
| Task substrate | In-process state, no queue | Postgres queue + leases + budgets + retry + `ownerToken` fence |
| Evidence layer | Context is a concatenated string | Structured evidence bank (`insight` / `quote` / `sourceUrl` kept separate, stored as JSON) |
| Citations | Soft constraint inside the prompt | Authorized-source set (only URLs that were retrieved *and* extracted may be cited) + mechanical References + canonical normalization |
| Quality evaluation | `evals/` (model quality) | Auditable evaluator: judge self-calibration + dual-metric accuracy + three-state hallucination falsification + two-run blind A/B judging |
| Source-quality gate | `SourceCurator`, default off | Same mechanism, once flipped to default-on; later flipped back to default-off after measurement showed it discards material (see table above) |

**Same-question comparison** (each implementation run once; six-dimension blind judging with
order-swapped re-runs, only consistent results accepted):

| Round | Items | `overall` | Note |
|---|---|---|---|
| 2026-09-13 | 4 | **2 : 2** | This project led 2:1 on depth / citation / honesty |
| 2026-09-20 | 2 | **2 : 0 (this project)** | One "opinion-type" item flipped from the original's 5-dimension lead |
| 2026-09-23 | 4 | 3 items to this project, 1 item reversed across runs (void) | Across 8 judge runs: depth 6:2 and honesty 7:1 to this project; structure 1:7 and language 1:7 to the original; citation 3:4 — **a wash** |

Taken together the two are **complementary** rather than one-sided: this project is stronger on
**analytical depth and honesty** (it labels the state of its evidence and separates inference from
fact), while the original is stronger on **structure that tracks the question and on prose**
(sections map to the question, less repetition, tighter sentences). In the last round the two raw
reports were also read by hand to check the judge's claims: three held up, one ("this project relies
on a single blog") was overstated — that blog is about half of its citations, but it also cites 22
arXiv and 8 Springer primary sources, whereas the original cites no primary academic source at all.

⚠️ **Boundaries**: only 2–4 items, one judge per item per round; two of the original's rounds reuse
older reports (not re-run under aligned conditions); judge and subjects share the same base model.
Both the table above and the "citation consistency 1.00 / contradictory claims 0" figure earlier are
directional only, **not a general superiority claim**.

## Retrieval and Scraping (pluggable)

- Retrieval fallback chain `gptr.clients.search-chain` (comma-separated, tried in order),
  **default `python,duckduckgo`**:
  - `python` — the in-repo `crawler/` service (20 search-engine adapters; the full-fat option)
  - `duckduckgo` — zero-key direct (Java-native)
  - `name:ok|transient|quota|permanent` — mock sources (tests / demos)
- The per-task retriever is set by the task config's `retriever` field (e.g. `searx` / `bocha`);
  **specify it explicitly** — the default one is unavailable in some network environments, and
  omitting it shows up as "all sub-queries failed".
- Key-type settings (per-retriever API keys, model, search chain) can also be persisted in the
  dashboard's config panel (worker restart required; no hot reload).

## Evaluation

The evaluator ships with judge self-calibration. Each run reports dual-metric accuracy (conditional
and strict full-sample), hallucination rate (conservative lower bound / upper bound including
inconclusive), citation consistency and citation coverage, and supports two-run blind A/B judging.

```bash
mvn -pl gptr-benchmark test       # unit tests for the evaluator itself; the main classes and
                                  # arguments for a real evaluation run are documented in BUILD.md
```

## Repository Layout

```
gptr-java/
├── docker-compose.yml        # Postgres + MinIO + crawler (+ optional searxng)
├── searxng/                  # optional retrieval source: settings.yml.example template (local config is not committed)
├── crawler/                  # stateless Python crawler service (extracted from gpt-researcher, Apache-2.0)
├── gptr-common/              # domain model / state machine / JPA / Flyway / task service / event log
├── gptr-integration/         # external client interfaces / resilience (retry, breaker, fallback) / report storage / UrlSecurity
├── gptr-engine/              # research engine: LangGraph4j graph / section-wise writing / evidence bank / citation verification
├── gptr-api/                 # REST + WebSocket + single-page dashboard (/dashboard/)
├── gptr-worker/              # queue consumer (dequeue / lease / budget / storage)
├── gptr-benchmark/           # evaluator (accuracy / hallucination / citation / coverage + A/B + micro-gold)
└── BUILD.md / README.md      # build-test guide and usage guide
```
